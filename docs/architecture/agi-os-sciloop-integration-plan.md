# AGI OS ↔ SciLoop Integration Plan

Status: architecture proposal; no product implementation is included in this document.

## Executive summary

AGI OS should remain the private research operating system. SciLoop should remain the polished, reviewed scientific product. The bridge between them should exchange versioned, immutable research artifacts rather than share runtime state, database tables, model credentials, or renderer code.

The recommended first integration is a pull/import workflow:

```text
AGI OS research
  → frozen research artifact
  → candidate visual package
  → SciLoop import boundary
  → schema, evidence, and semantic validation
  → human scientific and accessibility review
  → protected workbench preview
  → explicit promotion to public SciLoop
```

The first bridge should be a file/package contract with an authenticated upload or controlled repository handoff. It should not make SciLoop call AGI OS during public requests. This preserves the current public boundary, permits either system to be unavailable, and makes every promoted visual reproducible and rollbackable.

The existing SciLoop `PredictiveVisualPackage` is the closest internal bridge contract. It already carries evidence, sources, semantic nodes and edges, scenarios, assumptions, risks, unknowns, and provenance, and it is compiled deterministically into a SciLoop-owned `VisualRecipe`. It should be treated as the target semantic shape, not as proof that an AGI OS integration endpoint already exists.

## System responsibilities

### AGI OS: private research system

AGI OS owns:

- research questions, source collection, notes, hypotheses, and open questions;
- candidate reasoning graphs and visual hypotheses;
- experiment setup, candidate freezing, execution traces, comparison, lineage, and research notes;
- frontier-intelligence ingestion and research-derived evidence preparation;
- exploratory AI generation and simulation, clearly labeled as candidate or uncertain;
- private research identity, access control, and researcher-only data;
- export of an immutable review package with provenance and validation evidence.

AGI OS does not own public copy, public route availability, final renderer behavior, public accessibility claims, or final scientific promotion.

### SciLoop: product and publishing system

SciLoop owns:

- normalization into the canonical semantic package;
- evidence, source, uncertainty, and assumption treatment at the product boundary;
- deterministic recipe compilation and renderer selection;
- accessible fallback, public explanations, interaction design, and performance budgets;
- workbench preview and review workflow;
- public capability registry, route exposure, production telemetry, rollback, and release history;
- public APIs and any secrets used by the public product.

SciLoop must not depend on an AGI OS request completing during a public page load.

## Current SciLoop architecture

```text
Public request
  → proxy.ts allowlist / redirect policy
  → /sciloop-live route handler
  → preserved portal HTML and same-origin assets

Workbench request (where deployment/proxy policy allows it)
  → Next.js App Router pages and API route handlers
  → typed data and deterministic pipelines

  → ForLoop adapter or controlled AI backend
  → fallback output when unavailable

Legacy or experimental systems
  → server/ and backend/reality-engine/
```

Relevant SciLoop layers:

1. `app/` contains public, workbench, and API entrypoints.
2. `src/physics-visual-language/` contains the canonical physics semantic contract and recipes.
3. `src/visual-engine/foundation/` contains the engine-neutral visual recipe and predictive visual package contract.
4. `src/visual-engine/engines/`, `patterns/`, `renderer/`, and `memory/` provide routing, reusable forms, rendering, and reviewed-memory concepts.
5. `src/possibilities/` provides evidence briefs, scenarios, visual specifications, and validation.
6. `lib/capability-registry.ts` defines the workbench/candidate/public lifecycle.
7. `docs/architecture/shipping-boundary.md` defines the public/workbench and legacy boundaries.

The important existing seam is already present: validated semantic data is compiled into a SciLoop-owned recipe before rendering. The missing piece is a durable, authenticated, cross-repository artifact handoff and review record.

## Current AGI OS architecture

```text
AGI OS Next.js App Router
  ├── research workspace and notes
  ├── SciLoop Flow / cognitive engine laboratory
  ├── candidate graphs, freeze/run/history/lineage
  ├── experiments, evaluation, and protocol reports
  ├── frontier intelligence and ingestion cron
  ├── Maths AI and verified experiment artifacts

  └── auth and protected API routes
          ↓
      Prisma client → PostgreSQL
```

The current platform is suitable for producing research records and candidate packages, but its local cognitive-lab persistence and structural evaluation should not be treated as a public scientific validation service. The bridge must preserve the distinction between `HYPOTHESIS`, `INFERRED`, `SIMULATED`, and `OBSERVED` evidence.

## What should remain separate

- Repositories, deployment projects, release branches, and CI pipelines.
- Databases and database credentials. SciLoop should never connect directly to AGI OS PostgreSQL.
- User identities and sessions. A SciLoop public visitor should not be implicitly authenticated into AGI OS.
- Research notes, raw source material, private prompts, provider keys, internal graph mutations, and personal-system data.
- Experimental model runtimes, autonomous loops, and frontier ingestion jobs.
- Public route ownership and public copy approval.
- Renderer implementation. AGI OS can describe visual intent; it must not ship arbitrary SVG, Canvas, WebGL, JavaScript, or executable code into SciLoop.
- Public telemetry and research telemetry. They may be correlated through opaque artifact IDs, but should not be merged by default.

## What should be shared

Only the smallest stable, versioned artifact surface should cross the boundary:

- artifact ID, schema version, source AGI OS project/candidate ID, and engine version;
- research question and intended understanding goal;
- semantic nodes and directed relations with explicit meaning;
- evidence references and source metadata sufficient for SciLoop review;
- assumptions, risks, unknowns, falsifiers, and uncertainty classification;
- proposed quantities, controlled variables, measured outputs, and scenario definitions;
- visual hypotheses expressed as semantic primitives, not renderer code;
- reproducibility metadata: experiment ID, candidate freeze ID, run IDs, input references, output hashes, and generated timestamp;
- review state and immutable decision history once the package enters SciLoop.

The artifact should omit secrets, user-private notes, raw credentials, arbitrary code, direct database references, and provider-specific runtime instructions.

## Recommended integration model

### Phase-zero: contract-first, file/package handoff

Start with a repository-neutral JSON package that is compatible with SciLoop’s `PredictiveVisualPackage` after an explicit adapter mapping. Store exports as immutable artifacts with a content hash. A human or controlled job imports the artifact into the protected SciLoop workbench.

This is the safest first step because it works when either system is offline, supports manual scientific review, is easy to diff, and avoids inventing an AGI OS API that does not yet exist.

### Proposed package envelope

This is a proposal, not an existing API:

```ts
type ResearchVisualArtifact = {
  schemaVersion: "agi-os-research-visual/0.1";
  artifactId: string;
  createdAt: string;
  source: {
    system: "agi-os";
    repository: string;
    commit?: string;
    deployment?: string;
    researcherId?: string;
  };
  research: {
    question: string;
    hypothesis?: string;
    understandingGoal: string;
    experimentId?: string;
    candidateId?: string;
    candidateFreezeId?: string;
    runIds?: string[];
  };
  evidence: Array<{
    id: string;
    label: string;
    classification: "OBSERVED" | "MEASURED" | "INFERRED" | "SIMULATED" | "HYPOTHESIS" | "UNKNOWN";
    citation?: string;
    locator?: string;
    summary: string;
  }>;
  semantics: {
    nodes: Array<{ id: string; label: string; description: string; kind: string; certainty: string; evidenceIds: string[] }>;
    edges: Array<{ id: string; from: string; to: string; label: string; kind: string; strength?: number; evidenceIds: string[] }>;
    variables?: Array<{ id: string; label: string; unit?: string; range?: { min: number; max: number }; description: string }>;
    scenarios?: Array<{ id: string; label: string; assumptions: string[]; expectedOutcome: string; falsifiers: string[] }>;
  };
  visualHypothesis: {
    pattern?: string;
    primitives: string[];
    readingOrder: string[];
    interactionIntent?: string[];
  };
  assumptions: string[];
  risks: string[];
  unknowns: string[];
  provenance: { engineId: string; engineVersion: string; outputHash: string };
};
```

The SciLoop adapter should map this envelope into `PredictiveVisualPackage`, preserve every evidence classification, reject unsupported kinds, and attach a provenance record. The adapter must fail closed when required evidence or semantic references are missing.

### Phase-one: protected import and review record

Add a workbench-only import boundary in SciLoop. The exact route and storage technology require implementation approval, but the behavior should be:

1. accept an artifact or artifact reference only from an authenticated trusted source;
2. validate schema, size, content type, hash, evidence references, node/edge references, and allowed enum values;
3. persist the original artifact immutably or to an append-only object store;
4. create an import record with status `received`, `rejected`, `candidate`, `in-review`, `approved`, `promoted`, or `rolled-back`;
5. compile only validated semantics into a SciLoop recipe;
6. expose the candidate in the protected workbench, never public navigation;
7. require separate scientific and product/accessibility decisions before promotion.

### Phase-two: controlled pull or webhook notification

After the package has been used manually, add an authenticated AGI OS export endpoint or a SciLoop pull job. Prefer SciLoop pulling a specific immutable artifact by ID over AGI OS pushing arbitrary content to a public endpoint. A webhook, if later needed, should contain only an artifact ID and content hash; SciLoop should fetch the immutable package through a scoped service credential.

### Phase-three: promotion and release linkage

Promotion should create a SciLoop release record linking:

- imported artifact ID and hash;
- normalized package version;
- compiled recipe ID/version;
- renderer implementation version;
- source and evidence references;
- reviewer identities and decisions;
- accessibility/performance checks;
- public capability ID and route;
- previous public version for rollback.

The public product consumes only the approved SciLoop release record or a build-time snapshot. It does not fetch AGI OS at request time.

## Candidate lifecycle and workflow

```text
AGI OS draft
  → candidate frozen
  → reproducible run(s)
  → research report / review package
  → SciLoop received
  → schema and evidence validation
  → candidate visual recipe
  → scientific review
  → accessibility and product review
  → workbench preview
  → promotion decision
  → public release
```

Required invariants:

- A draft cannot be imported as approved content.
- A frozen candidate must identify the exact graph and source snapshot used.
- A `HYPOTHESIS`, `SIMULATED`, or `UNKNOWN` result cannot silently become a public fact.
- A recipe cannot render an edge that points to an unknown node or evidence ID.
- A public release must be reproducible from an immutable package and a known SciLoop renderer version.
- A rejected or rolled-back package remains auditable and is not overwritten.

## Scientific validation and human review

AGI OS’s structural evaluation is useful research evidence but is not by itself scientific validation. SciLoop should require at least:

1. source and citation review;
2. claim/evidence classification review;
3. semantic relation and unit review;
4. uncertainty, assumptions, risks, and falsifier review;
5. deterministic recipe validation;
6. renderer/fallback and accessibility review;
7. mobile/desktop and performance review;
8. explicit approval decision with reviewer, timestamp, and package hash.

For physics recipes, the package must map into the canonical Physics Visual Language contract and pass `validatePhysicsVisualRecipe()`. For general visual recipes, it must pass `validatePredictiveVisualPackage()` and `validateVisualRecipe()` after compilation.

## Rejected alternatives

### Direct AGI OS runtime dependency

Rejected for the public product. It creates availability coupling, latency, release coupling, and a path for research-only behavior to leak into production. It also makes rollback harder because the public result changes when the research system changes.

### Shared database or shared Prisma schema

Rejected. It couples migrations, credentials, retention, tenancy, and incident blast radius. Cross-system exchange should use explicit versioned artifacts.

### Copying AGI OS UI into SciLoop

Rejected. AGI OS is a research surface; SciLoop needs a curated product surface. A UI copy would blur ownership and expose internal workflows.

### Sending generated renderer code from AGI OS

Rejected. Renderer code is an executable supply-chain boundary. AGI OS should send semantic data and visual intent only; SciLoop compiles and renders it.

### Letting public visitors approve content

Rejected for initial promotion. Public feedback may inform later review, but scientific and product promotion requires an identified reviewer and a durable decision record.

### Automatic promotion based on scores

Rejected. Structural scores, model confidence, or aggregate readiness cannot replace evidence review and human approval.

## Security boundary

### Trust zones

```text
Zone A: AGI OS private research
  user auth · raw notes · provider keys · candidate graphs · experiments

Zone B: artifact exchange
  immutable package · hash · scoped credentials · validation receipts

Zone C: SciLoop protected workbench
  normalized package · recipe preview · review decisions · release candidate

Zone D: SciLoop public
  approved recipe snapshot · reviewed explanation · safe APIs · public telemetry
```

Rules:

- Never pass provider API keys, JWTs, cookies, raw prompts, private notes, or database URLs in an artifact.
- Use an allowlisted outbound path and short-lived, scoped credentials for future automated exchange.
- Validate content length, JSON depth, string lengths, enum values, URL schemes, and referenced IDs.
- Treat imported text, citations, and model output as untrusted data; do not execute it or interpret it as instructions.
- Store hashes and provenance before normalization so the original package can be compared to the imported record.
- Require replay protection using artifact ID plus hash/version; reject unexpected re-use or mutation.
- Keep AGI OS and SciLoop audit logs separate, linked only by opaque artifact IDs.
- Apply rate limits and timeouts to future import endpoints. Public routes must never proxy arbitrary AGI OS URLs.
- Require human approval for any transition to `public`.

The initial artifact exchange may be manual through a checked-in package or an internal upload. Do not introduce an object store, queue, or third-party integration until ownership, retention, access policy, and cost are approved.

## Data flow

1. Researcher creates a question and candidate in AGI OS.
2. AGI OS collects sources, records evidence classifications, builds a candidate graph, freezes the candidate, and runs the configured experiment.
3. AGI OS generates a review package containing the graph, experiment/run references, visual hypothesis, evidence, assumptions, risks, unknowns, and provenance.
4. The package is exported with a schema version and content hash.
5. SciLoop workbench imports the package through a non-public adapter.
6. SciLoop validates structure, references, evidence requirements, allowed semantics, and package provenance.
7. SciLoop maps valid package content to `PredictiveVisualPackage` and compiles a deterministic `VisualRecipe`.
8. Reviewers inspect the explanation, fallback, sources, uncertainty, renderer behavior, accessibility, and performance.
9. An approved candidate is associated with a capability-registry entry and release record.
10. The public build receives the approved snapshot. The public app never queries AGI OS while rendering.

## Implementation phases

### Phase 0 — confirm boundaries

- Confirm repository ownership, deployment URLs, operators, data classification, and review roles.
- Decide whether the first handoff is a file, signed repository artifact, or internal object store.
- Confirm whether SciLoop’s `PredictiveVisualPackage` remains the canonical bridge or needs a new versioned envelope.
- Define retention and deletion policy for imported research artifacts.

### Phase 1 — contract and fixtures

- Write the versioned artifact schema and examples for one physics concept and one non-physics concept.
- Add schema fixtures for valid, invalid, stale, unknown-evidence, unsupported-kind, and prompt-injection-shaped inputs.
- Define mapping rules from AGI OS candidate nodes/edges and experiment reports to SciLoop predictive semantics.
- Keep the contract documentation-only until the owners approve it.

### Phase 2 — protected import

- Implement a workbench-only import boundary and immutable import record.
- Store original package, hash, normalized package, validation receipt, and rejection reason.
- Add reviewer decision states and append-only audit events.
- Do not expose imported content through public navigation or public APIs.

### Phase 3 — preview and review

- Compile validated packages to deterministic SciLoop recipes.
- Add workbench preview, source/evidence panels, accessible fallback, and review checklists.
- Run browser, accessibility, performance, and offline checks before any promotion.

### Phase 4 — controlled automation

- Add scoped authenticated pull or notification only after the manual workflow is stable.
- Make imports idempotent and replay-safe.
- Add delivery status, retry, timeout, and dead-letter handling without blocking public requests.

### Phase 5 — public promotion

- Connect approved releases to `lib/capability-registry.ts`.
- Promote only reviewed snapshots through `workbench` → `main`.
- Preserve the previous public version and rollback pointer.
- Monitor provenance, renderer errors, fallback rate, and user understanding signals separately from AGI OS research telemetry.

## Rollback plan

### Artifact or adapter rollback

- Mark the import or normalized package `rejected` or `rolled-back`.
- Disable the affected candidate capability in the workbench.
- Keep the original artifact, hash, validation receipt, and review decision for audit.
- Stop automated pulls or notifications using the exchange feature flag.

### Public release rollback

- Repoint the capability to the last approved recipe/renderer release.
- Restore the prior public build or route snapshot through the normal deployment rollback mechanism.
- Do not delete the problematic artifact or public evidence; mark its status and reason.
- Confirm that public pages no longer resolve the new capability and that the preserved portal remains available.

### Security rollback

- Revoke the exchange credential, disable the import endpoint, and block the AGI OS source identifier.
- Rotate credentials if exposure is suspected.
- Review artifact contents and audit logs for secret leakage or instruction injection.
- Re-enable the bridge only after a new validation fixture and human security review pass.

## Decisions required before implementation

- Who can approve scientific, accessibility, and public-product promotion decisions?
- Is the bridge one-way AGI OS → SciLoop, or will SciLoop send review feedback back to AGI OS?
- Which artifact storage and retention model is acceptable?
- What is the minimum evidence required for each subject domain?
- Should imported packages be tenant-specific or product-global?
- Is an AGI OS deployment URL and service identity available for controlled automation?
- Which parts of the existing AGI OS visual-engine builder are research-only and which are intended to emit exportable semantics?

## Recommendation

Proceed with a documentation-approved, file/package-based bridge first. Treat AGI OS as a producer of auditable research artifacts and SciLoop as the sole compiler, reviewer, renderer, and publisher. This follows the boundaries already present in both repositories, preserves the public SciLoop route, and leaves room for a secure pull API after the artifact contract has proven useful in manual review.
